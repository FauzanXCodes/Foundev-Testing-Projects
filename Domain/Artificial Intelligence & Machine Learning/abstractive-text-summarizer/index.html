Consistency backend unavailable

This project ships a lightweight consistency service (src/api.py, engine: lexical entailment heuristic) that answers the UI’s POST /verify contract. The neural FactCC/FactCCX pointer–BERT checkpoints are not bundled with the repository and require the pinned 2020 dependency stack, so the service does not load them.

  1. Start the service: 
    python src\api.py
  2. Install its (lightweight) dependency if needed: pip install flask
  3. Then press Run consistency check again.

For a real neural verdict you would install the pinned Python dependencies (pip3 install -r requirements.txt), download an external checkpoint (factcc-checkpoint.tar.gz / factccx-checkpoint.tar.gz), and run modeling/run.py — see the API contract panel at the bottom of this page.

Desk notes

What FactCC does

A weakly-supervised model that (1) classifies whether a summary sentence stays factually consistent with its source, (2) extracts a supporting span in the source, and (3) extracts the inconsistent span in the summary if one exists. Trained on synthetically transformed CNN/DailyMail sentences.

How this desk treats honesty

No checkpoint ships in the repo, so the run button only explains what a real backend needs. The walkthrough is a hand-authored example whose spans are computed from your live text — it is always stamped demo and never presented as a model prediction.

Paper

Kryściński, McCann, Xiong, Socher — Evaluating the Factual Consistency of Abstractive Text Summarization, arXiv:1910.12840 (2019).

API contract & real CLI reference

This repository contains no HTTP server. Everything below documents the data format the code actually reads, the CLI that actually runs, and — clearly separated — a proposed contract for a future wrapper service.

1. Data format consumed by the repository (real)

One JSON object per line in a jsonl file, with keys id, text (source document) and claim (summary sentence). Evaluation scripts expect the dev file to be named data-dev.jsonl:

{"id": "example-001", "text": "<source document>", "claim": "<summary sentence>"}

2. Proposed HTTP contract for a future backend (not implemented here)

POST /verify
Content-Type: application/json

{
  "text":  "<source document>",
  "claim": "<summary sentence>"
}

→ 200 OK
{
  "label": "CORRECT" | "INCORRECT",   // FactCC label space (utils.py)
  "confidence": 0.0-1.0,
  "supporting_spans":    [ { "start": 0, "end": 0, "text": "..." } ],
  "inconsistent_spans":  [ { "start": 0, "end": 0, "text": "..." } ]
}

3. The real CLI (what actually executes today)

Entry point: modeling/run.py (argparse). The repository's modeling/scripts/ ships quickstart shell scripts; the evaluation script for FactCC is factcc-eval.sh:

python3 modeling/run.py \
  --task_name factcc_annotated \
  --do_eval --eval_all_checkpoints --do_lower_case --overwrite_cache \
  --max_seq_length 512 --per_gpu_train_batch_size 12 --model_type bert \
  --model_name_or_path bert-base-uncased \
  --data_dir <DATA_PATH> --output_dir <CKPT_PATH>
  • FactCC uses --model_type bert; FactCCX uses --model_type pbert (pointer–BERT, the span-extracting variant).
  • Task names in modeling/utils.py: factcc_generated (synthetic training data) and factcc_annotated (manually annotated validation/test data).
  • Checkpoints are external downloads (Google Cloud Storage links in the README): factcc-checkpoint.tar.gz / factccx-checkpoint.tar.gz.
  • Install deps with pip3 install -r requirements.txt; datasets must be paired with original CNN/DailyMail stories via data_pairing/pair_data.py.
